Operating it

Testing & status

Roughly 300 assertions, most of them over the real HTTP surface rather than against mocks. Plus an honest account of what is not finished.

The suites

These need nothing running but a database:

pnpm lint              # Biome, across the whole workspace
pnpm typecheck         # all five packages
pnpm test              # 139 unit tests, no database or .env needed
pnpm test:integration  # needs a live database
pnpm build             # production build

These drive a running server with the credentials the seed printed:

pnpm smoke <api_key> <device_token> <device_id> [<token_2> <id_2>]
pnpm smoke:checkout <api_key>
pnpm smoke:ingest <api_key>
pnpm smoke:audit <api_key>
pnpm smoke:stress <api_key>

Three things that will confuse you

Run the suites a minute apart. They share a per-IP rate limit, so back-to-back runs from one machine throttle each other. That is the limiter working, not a failure.

Run smoke:audit against next start, not next dev. The dev server answers dynamic pages with a different Cache-Control than production does, so one check fails spuriously and sends you looking for a leak that is not there.

pnpm smoke deliberately degrades an account to exercise drift detection, and leaves it that way. Re-run pnpm db:seed to re-anchor it, or later suites will fail with no_healthy_account.

What is verified

bKash works end to end, against real transfers rather than invented ones. Three live captures sit in the parser fixtures:

  • A received payment with a reference — the case automatic matching depends on.
  • The same without one, which must not auto-match, and does not.
  • A *247# confirmation, proving the reference survives USSD as well as the app.

The third doubles as the guard against the worst failure available: it is an outgoing message. If the watched phone ever sends money, it receives one of those, and it carries a TrxID, a reference, an amount and a balance — everything the matcher reads. Reading one as income would credit an order with money that went the other way.

What stops that is the transaction type, not a failure to parse. Matching admits send_money and nothing else, so an outgoing row is inert however completely it reads. It used to be stopped by failing to parse instead, and that cost three kinds of noise: a high-severity parse alert on every transfer the operator made, a permanent manual-queue entry, and immunity from the capture settings, since an unreadable message is always kept. Fixtures pin both the type and the fact that the sender field stays empty.

The live captures also pinned the timestamp handling: 04/09/2026 19:54 is read as the fourth of September at UTC+6. That is what the payment window measures against, and reading it wrongly refuses real payments silently rather than failing loudly.

Known gaps

Nagad is not implemented

The message format is unknown, so the parser is a deliberate stub that fails loudly rather than guessing. Nagad captures store their raw text and wait for a human; checkout lists Nagad as unavailable. One real message closes this.

Android capture is emulator-only

Pairing is proven on an emulator against the production server — App Links verify, the QR decodes from a screenshot, a device provisions end to end. But no emulator has a SIM or a wallet app, so capture itself and reboot survival are unproven on hardware. That is the gap that matters: forwarding messages is the app's whole job.

Rate limiting is per-instance

It is in-process. Fine on one instance; behind several the effective limit multiplies. The per-intent submission limit is database-backed either way.

The Messages bridge is unproven

Off by default, best-effort, and never held a real pairing. It relays through the phone, so it is not redundancy for the phone being off.

One operational risk that is not code

Providers distinguish personal accounts from merchant accounts. bKash separates a personal account from a merchant or Personal Retail Account, and sustained business traffic on a personal number risks a freeze. A frozen number takes the whole service down, not one payment. If volume is going to be real, get the right kind of account.
