# Versioning and releases

One version for the whole product. `VERSION` at the repository root is the only
place it is written down.

```
1.1.0
```

Everything else reads from it:

| Reads it | How |
| --- | --- |
| Five `package.json` files | `pnpm version:set` writes them; CI fails if they drift |
| `apps/android/app/build.gradle.kts` | reads `VERSION` directly at configure time |
| The notifier's heartbeat (`app_version`) | `BuildConfig.VERSION_NAME`, so the dashboard shows which build a phone is on |

They share a number because they ship together. A phone reporting one version to
a server running another is a support conversation nobody can win — and before
this, five `package.json` files said `0.1.0` while the Android app said `1.0.0`
and neither was true.

## Changing it

```bash
pnpm version:set 1.2.0   # exact
pnpm version:set minor   # bump
pnpm version:print       # what is it now
pnpm version:check       # what CI runs
```

Never edit `VERSION` by hand. The script is not ceremony — it enforces the one
rule below that has a silent failure mode.

### When to bump

Ordinary semver, read from the perspective of somebody integrating against the
API or running a phone:

- **patch** — a fix that changes no interface. Parser corrections, UI copy,
  anything invisible to a client app.
- **minor** — new capability that existing integrations do not have to care
  about. A new endpoint, a new setting, a new capture type.
- **major** — anything already-working stops doing what it did. A removed or
  renamed endpoint, a changed response shape, a database migration a running
  deploy cannot survive.

Deleting `POST /device/v1/provision` was a major-shaped change made at `1.x`
because nothing had been released yet and no device could have been holding a
QR from it. That reasoning has to be written down when it is used; the version
is a promise, and quietly breaking one is worse than incrementing the first
digit.

### The constraint that bites

Android needs a version code — an integer that must never decrease for an
installed app, or the update is refused *on the phone*, silently, long after
anyone is looking. It is derived:

```
1.4.2  ->  1 * 10000 + 4 * 100 + 2  =  10402
```

So **minor and patch must stay below 100**. At `1.100.0` the arithmetic carries
into the next field, the code stops tracking the version, and updates start
failing on devices you cannot see. `scripts/version.mjs` refuses to write such a
version, which is the main reason to use it rather than an editor.

A pre-release suffix (`1.2.0-rc1`) shares a version code with the release it
precedes. Fine for a test build handed to one phone; do not publish two of them
expecting an in-place update.

## Releasing

Two ways, both in `.github/workflows/release.yml`.

**By tag** — the normal path:

```bash
pnpm version:set 1.2.0
git commit -am "Release 1.2.0"
git tag v1.2.0
git push origin main v1.2.0
```

The workflow refuses a tag that disagrees with `VERSION`, so `v1.2.0` cannot
publish something built from `1.1.0`.

**By hand** — Actions → Release → *Run workflow*. This exists for forks: a fork
inherits the workflow but not the tags, and its owner should be able to get an
installable APK out of their own build without pushing a tag.

Both run the full suite first. A release is the artefact people install without
looking, so it does not get a weaker gate than a pull request.

### What gets published

| File | What it is |
| --- | --- |
| `jomma-notifier-<version>-debug.apk` | Installable anywhere, signed with `apps/android/debug.keystore`. Every ABI. |
| `jomma-notifier-<version>-release.apk` | Minified, arm-only, signed with the project key. Roughly half the size. |
| `SHA256SUMS.txt` | Checksums, generated by the build that produced the APKs. |

### Why the debug keystore is in the repository

Left to itself, the Android plugin generates a debug keystore per machine —
and CI runners are ephemeral, so that meant a new key on every release. Nobody
noticed until the app learned to update itself and the install failed at the
last step with "package conflicts with an existing package": Android refuses an
update whose signature does not match, and no two published debug APKs matched.

So `apps/android/debug.keystore` is committed, with the plugin's own well-known
debug credentials. It is not a secret and is not treated as one. It signs no
release — that key stays in repository secrets and never touches the tree — and
the only property it gives up is one debug builds never had: a debug-signed APK
is not evidence of origin.

### Signing, and what a fork gets

The release APK needs a key. Four repository secrets:

| Secret | Value |
| --- | --- |
| `ANDROID_KEYSTORE_BASE64` | `base64 -w0 your.jks` |
| `ANDROID_KEYSTORE_PASSWORD` | store password |
| `ANDROID_KEY_ALIAS` | key alias |
| `ANDROID_KEY_PASSWORD` | key password |

Optionally the `JOMMA_HOST` repository *variable*, so a fork builds App Links
for its own domain instead of this one's.

Without them the workflow still runs and still publishes — the debug APK only,
saying why in the release notes. That is deliberate: an unsigned release APK
cannot be installed, so shipping one would be shipping something useless.

> A fork that signs with its own key must publish its own fingerprint, or
> provisioning QRs will open a browser instead of the app. `./gradlew
> :app:printSigningFingerprint` prints it and `docs/android.md` explains where
> it goes. The release workflow prints it too, from the APK it just built.

Keep the keystore. Losing it means no future build can update an installed copy
— Android refuses an update signed by a different key, and the only way out is
uninstalling every phone and provisioning it again.
