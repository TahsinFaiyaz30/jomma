Understanding it

Matching rules

The part worth understanding, because it decides whether money reaches the right order. Jomma answers with a hard yes or a hard no — there is no score to tune and no threshold to cross.

The six rules

A payment is credited automatically only if every one of these holds. The first that fails names the refusal, and the payment is kept and surfaced rather than dropped.

#RequirementRefusal if it fails
1The message parsed, and the amount is above zerounparsed, amount
2It arrived on this intent's receiving numberaccount
3The reference matches the code exactlyreference_missing, reference_inexact
4The intent declared a payer numbersender_undeclared
5The sender is that numbersender_mismatch
6The provider's timestamp falls inside the checkout windowbefore_window, after_window

The logic is a single function with no I/O, which is why it can be tested exhaustively without a database:

export function admits(payment, intent): Refusal | null {
  if (payment.amountCents === null) return 'unparsed'
  if (payment.amountCents <= 0) return 'amount'
  if (payment.receivingAccountId !== intent.receivingAccountId) return 'account'

  const reference = normalizeRef(payment.referenceRaw)
  const code = normalizeRef(intent.refCode)
  if (!reference || !code) return 'reference_missing'
  if (reference !== code) return 'reference_inexact'

  if (!intent.expectedMsisdn) return 'sender_undeclared'
  if (!sameMsisdn(payment.senderMsisdn, intent.expectedMsisdn)) return 'sender_mismatch'

  const at = paymentTime(payment).getTime()
  if (at < intent.payClickedAt.getTime() - WINDOW_GRACE_MS) return 'before_window'
  if (at > intent.expiresAt.getTime() + WINDOW_GRACE_MS) return 'after_window'

  return null // credited
}

A refusal is never a deletion. The raw message is stored before anything tries to parse it. A refused payment appears in the dashboard feed with the reason attached, and an admin can apply it by hand or it can be re-parsed once a parser improves.

Why the amount is not a rule

Paying the wrong amount does not stop a match. Less than asked becomes a partial, more becomes an over, and both are recorded against the order. Nobody is refused for paying the wrong amount — they are refused for being unidentifiable.

An earlier design did the opposite: it held (account, amount) exclusively, so the reference was optional and the amount identified the order. That breaks immediately in the real world. The third customer to buy a Tk 500 item could not check out at all, because the amount was taken.

Matching on amount and phone number is the trap. It works until two people pay the same price from numbers the system has seen before, and then it silently credits the wrong customer. That is why the reference is mandatory and the amount is not a gate.

Reference codes

ABCDEFGHJKMNPQRSTUVWXYZ23456789     8 characters     7CX4Z8ZS

Thirty-one symbols, not thirty-six. 0, 1, I, L and O are gone, because a buyer reads the code off a screen and types it into a phone, and those five are where transcription errors come from.

  • About 852 billion combinations. Enough that guessing one that is currently live is not a practical attack.
  • Never reissued. A unique index over every code ever generated makes reuse impossible — not unlikely, impossible. A code belongs to exactly one order for all time.
  • Case-insensitive, punctuation-insensitive. Both sides are upper-cased and stripped of non-alphanumerics before comparison, so 7cx4-z8zs matches.
  • Never fuzzy. One character out is a refusal, not a near-miss. A fuzzy match on a payment code is a wrong credit waiting to happen.

Why there is no punctuation in a code

It would be stripped by the normaliser before comparison, so it could not contribute to identification at all. Whether a provider's reference field even preserves symbols is unverified, and they are harder to type accurately on a phone. Length is free entropy and does none of that damage.

The time window

The payment must have happened during this checkout. Money that moved before the buyer opened the page cannot be for this order, and money that moved after it expired is for whatever they did next. 

[ intent created - 5 min ] .............. [ expires_at + 5 min ]

Measured against the provider's own timestamp, parsed out of the message as Bangladesh time — not when Jomma received it. A phone that was switched off for an hour still matches correctly when it reconnects and flushes its queue.

That distinction is load-bearing and easy to get wrong. 04/09/2026 19:54 has to be read as the fourth of September, not the ninth of April, and as UTC+6 rather than the server's zone. Getting either wrong does not fail loudly: it silently refuses real payments as before_window, which is exactly the sort of bug that reaches production. There is a regression test pinning both.

Five minutes of grace at each end absorbs clock skew between the provider, the phone and the server.

Part and over payments

A buyer can pay in instalments against one reference code. Each capture is applied to the ledger and the intent's total is recomputed, so three payments of Tk 400, Tk 400 and Tk 450 settle a Tk 1,250 order without anybody intervening.

The buyer's page shows every instalment it has counted, with its TrxID. A second request for money with no account of the first reads as a mistake or a scam, so the ledger is shown rather than just the outstanding total.

How it stays correct under load

One write path

lib/services/apply.ts is the only code that credits an intent. Automatic matching, buyer TrxID submissions and admin approval all call it, so the cumulative-sum arithmetic and the row lock exist exactly once. There is no second implementation to drift.

A TrxID is spent once

A unique constraint, not a check-then-write. Twenty simultaneous claims on the same TrxID produce one credit and nineteen refusals, and the losers get a clean 409 rather than a 500.

Concurrent instalments serialise

Applying reads the intent FOR UPDATE, so five payments landing in the same instant each read the total the previous one wrote. Without it, two concurrent applies would both read zero and the order would appear half-paid.

These three are exercised by pnpm smoke:stress, which fires genuinely parallel requests and then asks the database whether the books balance: an intent's received total equals the sum of its unreversed applications, a TrxID is spent at most once, and nothing is credited twice.
