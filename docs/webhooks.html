Webhooks

How your store finds out that money arrived. Register a URL and a secret per app in the dashboard; delivery is at-least-once with retries.

The nine events

EventFires whenExtra fields
payment.succeededFull amount matched. The main one.—
payment.partialMoney arrived, short of the total.shortfall
payment.overpaidMore than the total arrived. The order is complete.excess
payment.expiredTTL elapsed with no payment.—
payment.cancelledYou cancelled, or an admin voided it.—
payment.reversedAn applied match was undone by an admin.—
payment.refund_requestedA buyer asked for money back from the pay page.reason, note
account.degradedA receiving number went unhealthy.reason
account.recoveredIt came back.—

payment.reversed deserves real handling. It means Jomma previously said money arrived and now says it did not — a match an admin undid. If your store cannot un-fulfil an order, you will ship goods for a payment that was withdrawn. It is rare and it is serious.

payment.refund_requested is a message, not an instruction. Jomma watches your accounts and has no authority over them; it cannot move money back. The event records that a buyer asked. You refund from your own system.

account.degraded is worth acting on. It usually means a phone stopped reporting. Checkout already routes around the account, but it is your early warning that payments may be arriving unseen.

Verifying the signature

The signed payload is the timestamp, a dot, and the raw request body. Three things go wrong most often:

  1. Signing a re-serialised body. Parsing JSON and stringifying it again changes whitespace and key order. Sign the bytes you received.
  2. Not checking the timestamp. A signature stays valid forever unless you bound it. Five minutes is the recommended window.
  3. Comparing with ===. Use a constant-time comparison, or you leak the signature a byte at a time.
import { createHmac, timingSafeEqual } from 'node:crypto'

export function verify(raw: string, header: string, secret: string): boolean {
  const t = header.match(/t=(\d+)/)?.[1]
  const v1 = header.match(/v1=([a-f0-9]+)/)?.[1]
  if (!t || !v1) return false

  if (Math.abs(Date.now() / 1000 - Number(t)) > 300) return false

  const expected = createHmac('sha256', secret).update(t + '.' + raw).digest('hex')
  const a = Buffer.from(expected)
  const b = Buffer.from(v1)
  return a.length === b.length && timingSafeEqual(a, b)
}

Or let the SDK do it:

import { constructEvent } from '@jomma/sdk'

const event = constructEvent(raw, signatureHeader, secret)

Retries

Delivery is at-least-once. Return any 2xx to stop the retries; anything else, or a timeout, schedules the next attempt. 

10s -> 1m -> 5m -> 30m -> 2h -> 6h -> 24h

After the last attempt the event is marked failed and waits in the dashboard under Apps > Deliveries, where you can replay it by hand once your endpoint is healthy.

Make your handler idempotent. The same event.id can arrive more than once — a retry after your 200 was lost in transit looks identical to a first delivery. Record processed ids, or make fulfilment safe to repeat.

Handling them well

Answer fast, work later

Verify, enqueue, return 200. Doing the fulfilment inline means a slow database turns into a retry storm, and your handler is racing a 10 second clock.

Do not trust the body before the signature

The endpoint is public. Anyone can POST it a payment.succeeded for any order id they can guess. The signature is the only thing separating a real event from a free order.

Treat the intent as the source of truth

If an event ever looks wrong, GET /v1/intents/:id is authoritative. The event is a notification about state, not the state itself.
