Operating it

Running Jomma

Jomma is self-hosted. You run the server, you hold the database, and the phone with your SIM in it is yours. Nothing about a payment leaves your infrastructure.

Running locally

Needs Node 22+, pnpm and Docker.

git clone https://github.com/TahsinFaiyaz30/jomma
cd jomma
pnpm install
cp .env.example .env

Generate the two secrets that .env needs, and paste them in:

node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
pnpm db:up        # Postgres 18 in Docker, on localhost:5433
pnpm db:migrate   # create the schema
pnpm db:seed      # prints an API key and device tokens ONCE

Then, in two terminals:

pnpm dev          # dashboard, API and pay page on http://localhost:3000
pnpm dev:worker   # the scheduler

Sign in at /login with the admin email and password the seed printed. There is no signup — accounts come from the seed or from another admin, and the sign-up endpoint is disabled outright.

Postgres 18 is required. Primary keys default to uuidv7(), which is core in 18 and absent in 17, so migrations fail immediately on an older server. On Neon, choose version 18 when you create the project — the default may be older.

db:seed is the development seed. It creates a demo app and two receiving accounts on numbers nobody owns, so the smoke suites have something to work with. It refuses to run against a non-local database: checkout routes real payments across every healthy account, so a live instance carrying those could hand a buyer a pay page telling them to send money to a stranger's number.

To bootstrap a deployment, run pnpm db:seed --admin-only. That creates the admin account and nothing else; you add your own receiving accounts, app and webhook endpoint from the dashboard.

Port 3000 taken? Use another, and set APP_URL to match:

PORT=3100 pnpm dev

If APP_URL disagrees with the address you are actually using, sign-in fails the origin check and looks exactly like a wrong password.

Secrets are validated at boot. A missing or obviously-wrong value stops the process with a message naming the variable, rather than failing later on a request that involved money.

The phone app

apps/android/ is a Kotlin app that forwards payment confirmations to your server. It is the only moving part that is not an ordinary web service.

Setting one up

  1. Install the APK on a phone holding your receiving SIM — from the releases page, taking the -release build. The -debug one is for development and is signed with a different key.
  2. In the dashboard, go to Accounts, pick the receiving number, and add a device. A provisioning QR appears and is valid for fifteen minutes.
  3. Scan it with anything. The phone's camera app, any scanner you already have, or the notifier's own scanner — which will also read the code out of a screenshot.
  4. Grant notification-listener and SMS-read permission. Run both paths — they fail independently.
  5. Send a small transfer and watch it appear on the Feed.

Why any scanner works

The QR contains one thing — a URL, https://your-host/pair/<one-time-code> — because a URL is the one payload every scanner app can act on. Android App Links then route it into the notifier with no chooser and no browser.

That routing is also the security boundary. Since Android 12 an app that cannot prove the domain endorses it does not receive the link and cannot register for it, so no other app can intercept a provisioning code. A custom jomma:// scheme would have been simpler and had the opposite property: any app may claim one.

Verification depends on your instance serving the APK's signing fingerprint at /.well-known/assetlinks.json. That works out of the box for builds of this repository; a fork signing its own APK sets ANDROID_CERT_SHA256. Until Android has verified — it asks Google's asset-links service, which caches for an hour — the link opens a browser, and that page hands off to the app with an intent:// URL naming the package, so scanning still reaches the notifier either way.

Nothing readable is in the QR — no token, no device id, no phone number. It used to be JSON carrying all three, which any scanner would happily display. The code is still a bearer credential for fifteen minutes and one use, so a screenshot of a live QR is worth guarding; the narrower claim is that a scanner showing what it read shows a host and an opaque string.

Tokens are hashed at rest, scoped to one receiving account, and individually revocable. A lost phone costs one device rather than the integration.

What it keeps

bKash shows the phone far more than payments. Accounts → What to capture has three switches — cash in, money you sent, everything else — and the same three are in the app, writing to the same row, so whichever screen is closer to hand wins.

Incoming Send Money has no switch, because it is the only type that can settle an order. Anything switched off is dropped when it reaches the server and never stored. A message the parser cannot read is kept regardless, as long as it looks like a transaction at all — that is the evidence needed to fix the parser.

It updates itself

There is no Play listing, so nothing updates this app unless it updates itself — and the phone that most needs a fix is the one nobody is looking at. Settings → Updates checks this project's GitHub releases once a day by default; weekly, monthly, every launch and never are the alternatives. A new version raises a notification once, and tapping it opens the Updates card.

It fetches the build matching the one installed — release for release, debug for debug. The two are signed with different keys, and Android refuses an update whose signature does not match, so offering the wrong one fails at the very last step with a message nobody can act on.

Installing is always your decision. Android requires the app to be allowed to install packages, per app, and then confirms the install itself; the app deep-links to that settings screen rather than failing with a permission error. Pre-download fetches the APK before you say yes and is off by default. Wi-Fi only is on by default and governs the download, not the check — the check is a few hundred bytes, the APK is twelve megabytes, and this phone is often on mobile data as its only link.

Keeping it alive

  • Turn off battery optimisation for the app, or Android will eventually stop it. Settings → Staying alive asks for it directly and shows whether it actually took.
  • On Honor, Huawei, Xiaomi, Oppo, Vivo and Samsung, also allow it in the vendor's own background-app screen — the same screen offers a shortcut to it. That setting is separate from Android's, and is the usual reason a notifier dies overnight while every Android setting reads as correct.
  • Leave it charging. The app survives reboot, but a dead phone captures nothing.
  • Watch for account.degraded — a silent phone raises it, and that is your early warning that payments may be arriving unseen.

Versions & releases

One version for the whole product, in VERSION at the repository root. Every package.json and the Android build read from it, because they ship together — a phone reporting one version to a server running another is a support conversation nobody can win. 

pnpm version:print         # what is it now
pnpm version:set 1.2.0     # set it everywhere
pnpm version:set minor     # or bump it

Never edit the file by hand. Android needs a version code derived from it (1.4.2 → 10402) that can never decrease for an installed app, so the script refuses a version that would break the arithmetic. At 1.100.0 the minor field carries into the next and updates start failing on phones nobody is looking at.

WorkflowRuns onDoes
CIevery push to main, every PR, or on demandtypes, lint, tests, Android unit tests, debug APK
Releasea v* tag, or on demandboth APKs, signed, published as a GitHub Release

A normal push does not cut a release. To cut one:

pnpm version:set 1.2.0
git commit -am "Release 1.2.0" && git push
git tag v1.2.0 && git push origin v1.2.0

The workflow refuses a tag that disagrees with VERSION, so v1.2.0 cannot publish a build of 1.1.0, and it runs the full suite before publishing anything.

A tag runs the workflow as it existed at that tag's commit. Change the workflow and re-tag without moving the tag onto the new commit and you will re-run the old one, which is a confusing way to lose an afternoon.

Forking

Both workflows offer Run workflow in the Actions tab, because a fork inherits the workflows but not the tags and should still be able to produce an installable APK from its own build.

Signing comes from four repository secrets:

SecretValue
ANDROID_KEYSTORE_BASE64base64 -w0 your.jks
ANDROID_KEYSTORE_PASSWORDstore password
ANDROID_KEY_ALIASkey alias
ANDROID_KEY_PASSWORDkey password

Plus an optional JOMMA_HOST repository variable, so the APK's App Links target your domain rather than this one's. Without the secrets the release still publishes — debug APK only, saying why. An unsigned release APK cannot be installed, so shipping one would be shipping nothing.

A fork signing with its own key must publish its own fingerprint in ANDROID_CERT_SHA256, or provisioning QRs open a browser instead of the app. ./gradlew :app:printSigningFingerprint prints it, and the release workflow prints it too from the APK it just built.

Keep the keystore. Losing it means no future build can update an installed copy — Android refuses an update signed by a different key, and the only way out is uninstalling every phone and provisioning it again.

Deploying

PieceWhereCost
API, dashboard, pay pageRender web service, Singapore$7/mo, or free with a caveat
Postgres 18Neon, Singaporefree
Schedulercron-job.org calling the sweep endpointfree

render.yaml in the repo is a working blueprint. There is no separate worker to deploy: every scheduled job lives in the web app under lib/jobs and is reached through one authenticated endpoint, so a cron ping does exactly what the worker does. 

POST /api/internal/sweep?group=all

Set APP_URL by hand, with the scheme. It is the one variable the blueprint cannot fill in, because Render's fromService returns a bare hostname and everything reading this needs an absolute URL. Put https://your-service.onrender.com on both the web service and the cron job once the first deploy has named them. Without it Better Auth rejects every sign-in and the cron cannot build a fetchable sweep URL, so no webhook is ever delivered — which is why the app now returns a 500 naming the variable rather than looking healthy.

Run the migrations and create the first admin from your own machine, once:

DATABASE_URL='postgres://...?sslmode=require' pnpm db:migrate

DATABASE_URL='postgres://...?sslmode=require' \
JOMMA_ADMIN_EMAIL='you@example.com' \
JOMMA_ADMIN_PASSWORD='...' \
pnpm db:seed --admin-only

That creates the admin and nothing else. Sign in, then add your own receiving accounts, your app and its API key, and a webhook endpoint.

Never use Render's own free Postgres. It is deleted after 30 days. That is not a database to put payment records in.

The free tier, honestly

A fully free deployment works. Two consequences you are accepting:

A sleeping web service cannot receive a payment

Render's free tier sleeps after 15 minutes and takes 30–60 seconds to wake. Nothing is lost — the phone retries from its local queue — but a buyer watching your checkout waits for that cold start. A one-minute cron ping keeps it awake in practice.

The cron interval is your webhook latency

Webhook delivery is driven entirely by the sweep, so however often the cron runs is how long your store waits to hear about a payment. That interacts with Neon's free compute allowance:

Cron intervalNeon compute / monthConsequence
1 minute~180 CU-hoursExceeds the 100 CU-hour free cap around day 16, and the database suspends.
10–15 minutes~60–90 CU-hoursFits, but your store waits that long for the webhook.

Buyers are unaffected either way. Matching happens inline on capture and the pay page polls every 2.5 seconds, so a buyer sees their confirmation immediately. Only the server-to-server notification waits.

For real money moving through it, the $7 Render Starter plan is the one upgrade that matters: it stops the web service sleeping, which is the only part a customer can see.

Backups and upgrades

Migrations are not automatic

On purpose. A migration that rewrites a payments table should be something a person runs while watching, not something a deploy does on its way past. Run pnpm db:migrate against production yourself, then deploy.

What to back up

The database, and nothing else. The application is stateless; every payment, intent, ledger row and audit entry is in Postgres. Neon keeps point-in-time restore on its free plan, which covers the common accident.

What not to lose

WEBHOOK_SIGNING_SECRET and AUTH_SECRET. Rotating the first invalidates every registered endpoint's verification until you update them; rotating the second signs everyone out.
