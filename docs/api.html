Reference

API

Three surfaces: the client API your store calls, the device API the phone app calls, and the public pay-page API the buyer's browser calls. All bodies are JSON, all money is integer poisha, all timestamps are ISO 8601 UTC.

Authentication

Authorization: Bearer jm_live_xxxxxxxxxxxxxxxxxxxx

Keys are Argon2-hashed at rest; the plaintext is shown once, at creation. The prefix (jm_live_ / jm_test_) is stored in clear for lookup and display. Revoking a key is immediate.

The pay-page endpoints under /api/pay/ take no key: the buyer is an anonymous visitor holding a link. They are rate-limited by IP and return only what a buyer needs. Putting an API key in a buyer's browser would be a far worse trade.

Intents

POST /v1/intents

Creates a payment request and allocates a reference code.

FieldTypeRequiredNotes
amountintegeryesPoisha. Tk 1,250.00 is 125000. Must be positive.
client_referencestringyesYour order id, 1–255 chars. Echoed on every webhook.
payer_msisdnstringeffectively yesThe number the buyer will send from. Without it nothing auto-matches.
providerenumnobkash, nagad, or any. Default any. Naming one stops the buyer changing it.
ttl_secondsintegerno60–3600. Default 300.
metadataobjectnoOpaque. Returned on every webhook for this intent.
return_urlstringnoWhere the hosted page sends the buyer on success.
cancel_urlstringnoWhere it sends them if they back out.

payer_msisdn is not really optional. Automatic matching refuses any payment whose intent has no declared sender, so an intent without it can only ever be settled by a manual TrxID submission. If you do not know the number, use the hosted pay page — it asks the buyer before showing them anything to pay.

Send an Idempotency-Key header, ideally your order id. Replaying it within 24 hours returns the original intent and a 200 instead of a 201. Without it a retried request allocates a second reference code, leaving the buyer with two live codes for one order where only one settles it.

return_url and cancel_url are checked against the hostnames registered for your app under Apps > Hosted checkout. An app with none registered gets no redirect rather than any redirect it asks for: an unchecked return URL on a payment page is an open redirect aimed at someone who was just told to trust that page. Subdomains of a registered host are allowed.

GET /v1/intents/:id

The full state of one payment. Poll every 2–3 seconds; the rate limit assumes it.

{
  "id": "int_01M1PEP3ZZEEC99NQ5CM1H6W1Q",
  "status": "matched",
  "amount": 125000,
  "received_amount": 125000,
  "ref_code": "7CX4Z8ZS",
  "receiving_account": {
    "provider": "bkash",
    "msisdn": "8801611223344",
    "display_name": "Your Shop"
  },
  "client_reference": "ORD-2026-001043",
  "payments": [
    {
      "trx_id": "DI4760E7CN",
      "sender_msisdn": "8801712345678",
      "amount": 125000,
      "occurred_at": "2026-09-04T13:54:00Z",
      "applied_at": "2026-09-04T13:54:06Z",
      "match_confidence": "exact",
      "matched_by": "automatic"
    }
  ],
  "shortfall": 0,
  "excess": 0,
  "metadata": { "store_id": "st_912" },
  "expires_at": "2026-09-04T14:05:00Z",
  "created_at": "2026-09-04T13:50:00Z"
}

payments is a list because a buyer can pay in instalments against one code. It is the ledger for that order, oldest first, and its amounts always sum to received_amount.

POST /v1/intents/:id/cancel

Expires the reference code immediately. Safe to call on an already-cancelled intent.

POST /v1/intents/:id/extend

{ "ttl_seconds": 900 } — useful when a buyer underpays and you want to hold the order while they top up. A matched or cancelled intent cannot be extended.

Intent statuses

StatusMeaningYour move
openWaiting for money.Show the pay page.
partialSome arrived, short of the total.Hold the order. The same code accepts the rest.
matchedPaid in full.Fulfil.
overMore arrived than asked.Fulfil, and settle the excess yourself.
expiredTTL elapsed with nothing.Release stock.
cancelledYou cancelled, or an admin voided it.Nothing.

over is a completed state, not a problem to resolve. The reference code is consumed and the order is done; the excess is a separate conversation.

Submissions

POST /v1/submissions

For a payment that did not auto-match, usually because the buyer skipped the reference field. The buyer supplies the TrxID from their own confirmation and Jomma looks for it among the payments it has already captured. 

{
  "intent_id": "int_01M1PEP3ZZEEC99NQ5CM1H6W1Q",
  "trx_id": "DI4760E7CN",
  "claimed_amount": 125000
}

The lookup is scoped to that intent's receiving account, and the sender still has to match the declared payer. Possible resolutions:

ResolutionMeaning
appliedFound, checks passed, credited.
partialCredited, still short. Response carries shortfall.
overCredited, more than asked. Response carries excess.
not_foundNo payment with that TrxID on this account. Usually too early.
sender_mismatchFound, but from a different number. Escalated to a human, never auto-applied.
already_appliedThat TrxID is already spent on this order.
duplicate_submissionSpent on a different order. Returns 409.

The public version, POST /api/pay/:id/submit, deliberately takes no sender number: a buyer supplying both the claim and the evidence for it is self-certifying. The number comes from the intent.

Accounts

GET /v1/accounts

Which receiving numbers exist and whether they are healthy. Worth calling before you show a payment option at all — an account is degraded when its phone has stopped reporting, or when its balance stopped adding up.

Pay-page API

Public and unauthenticated, used by the hosted checkout. Listed because you may want to build your own page against the same endpoints.

EndpointPurpose
GET /api/pay/:id/statusWhat the page polls. Buyer-safe subset: no order id, no account id, no other payments.
POST /api/pay/:id/payerThe buyer naming their number. Write-once, and only while open.
POST /api/pay/:id/methodThe buyer choosing a provider. Refused once money has arrived.
POST /api/pay/:id/submitManual TrxID verification.
POST /api/pay/:id/refundRecords a refund request. Jomma moves no money.
GET /api/pay/:id/qrA PNG QR of the pay page, for carrying it to a phone.

The intent id is a uuidv7 rendered as 26 base32 characters, so it is not guessable. That is what makes these safe to leave unauthenticated.

Building your own checkout

Nothing about the hosted page is required. POST /v1/intents returns everything you need; render it however you like and poll GET /v1/intents/:id with your API key.

Tell the buyer to:

  1. Open their wallet app and choose Send Money (or dial *247# and choose 1)
  2. Send to receiving_account.msisdn
  3. Enter exactly amount
  4. Put ref_code in the Reference field
  5. Confirm with their PIN

If you build your own page you must collect the buyer's number and pass it as payer_msisdn, or nothing will auto-match and every payment will need a manual TrxID.

SDK

pnpm add @jomma/sdk
import { Jomma } from '@jomma/sdk'

const jomma = new Jomma({
  apiKey: process.env.JOMMA_KEY,
  baseUrl: 'https://pay.yourshop.com',
})

const intent = await jomma.intents.create({
  amount: 125000,
  clientReference: order.id,
  payerMsisdn: order.buyerPhone,
  provider: 'bkash',
  returnUrl: 'https://yourshop.com/orders/' + order.id + '/thanks',
  idempotencyKey: order.id, // do not omit this
})

redirect(jomma.payUrl(intent.id))

Webhook verification, with the timing-safe comparison and staleness check already done:

import { constructEvent } from '@jomma/sdk'

const event = constructEvent(
  rawBody,
  req.headers.get('x-jomma-signature'),
  process.env.JOMMA_WEBHOOK_SECRET,
) // throws SignatureVerificationError on a bad or stale signature

The SDK is types, signing and retries. No business logic — anything that decides what a payment means lives on the server, where there is exactly one copy of it.

Errors

{
  "error": {
    "code": "no_healthy_account",
    "message": "No receiving account is currently accepting payments.",
    "request_id": "req_01J8X..."
  }
}
CodeHTTPWhat to do
unauthorized401Bad or revoked key.
not_found404Unknown intent. Also returned for another app's intent, deliberately — a 403 would confirm it exists.
validation_failed422Body rejected. details says which field.
duplicate_submission409That TrxID is already spent on another order.
rate_limited429Back off. Retry-After says how long.
no_healthy_account503Every receiving number is down. Do not show a pay page.

Every response carries request_id. Log it — it is searchable in the dashboard.

Rate limits

X-RateLimit-Limit, X-RateLimit-Remaining and X-RateLimit-Reset come back on every response, errors included.

EndpointLimit
POST /v1/intents60 / min per key
GET /v1/intents/:id600 / min per key
POST /v1/submissions20 / min per key, 5 / hour per intent
POST /device/v1/capture120 / min per device
POST /ingest/v1/webhook120 / min per IP

Limiting is in-process, so it is per instance. Fine on one instance; behind several, the effective limit multiplies. The per-intent submission limit is database-backed and holds either way.
