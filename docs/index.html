What it is

Jomma is not a payment gateway. There is no integration with any provider's servers and nothing to get approved. It reads the confirmation messages that arrive on a phone you already control, and answers one question with high confidence:

Which order does this payment belong to?

Jomma doesJomma does not
Issue a unique reference code per orderMove, hold, or refund money
Watch your receiving numbers for incoming transfersAsk for or store anyone's PIN
Match a transfer to an order — or refuse toGuess when it is unsure
Tell your store with a signed webhookNeed gateway approval
Handle part payments and overpaymentsCharge a percentage of anything

Who it is for

Anyone taking mobile-money payments in Bangladesh who cannot, or would rather not, go through a payment gateway: a shop on social media, a small storefront, a school collecting fees, a SaaS billing local customers. If you already accept transfers and someone currently checks the phone by hand, that person is what Jomma replaces.

Buyer checks outYour store calls POST /v1/intents and gets a reference code — 7CX4Z8ZS.
Buyer paysThey open their wallet app, send the exact amount to your number, and type that code into the Reference field.
The phone sees it"You have received Tk 1,250.00 from 018... Ref 7CX4Z8ZS. TrxID DI4760E7CN"
Jomma matches itReference, sender, time window and receiving account all have to agree. If any one disagrees, it refuses rather than guessing.
Your store is toldA signed payment.succeeded webhook lands on your endpoint.

Step three, in more detail

This is the part people ask about, because it is the only part that is not an ordinary web service. An Android phone with your SIM in it runs the Jomma notifier app. When a payment confirmation arrives, the app forwards it to your server over HTTPS with a device token.

  • Two independent paths. The app reads the provider's notification and its SMS. They fail for different reasons, so running both means one path breaking does not lose a payment.
  • Local queue first. Every capture is written to the phone's own database before it is sent, and only marked sent on a 2xx. A flat battery, a dead network or a sleeping server delays a payment rather than losing it.
  • Nothing is dropped on a parse failure. The raw message is stored before anything tries to read it, so a provider changing its wording costs an alert and a manual review, and the message can be re-parsed later.

There is also a signed webhook endpoint (POST /ingest/v1/webhook) if you have some other source of the same messages, and a manual paste box in the dashboard for when everything else is down.

One phone is a single point of failure for your whole revenue stream, which is why two receiving accounts are seeded by default. A degraded account is routed around rather than blocking checkout.

Providers

Everything except one file per provider is provider-agnostic.

Intents, reference codes, the matching rules, the ledger, webhooks, the dashboard and the hosted checkout know nothing about any particular wallet. They deal in "a message arrived on a receiving account". What is provider-specific is a parser: the regexes that turn one provider's confirmation text into an amount, a sender, a reference and a transaction id.

ProviderStatusWhat is missing
bKashLive, verified against real transfers Nothing. Three live captures in the fixtures; the app and *247# are both confirmed.
NagadStubbed, deliberately The message format. The parser fails loudly rather than guessing, and checkout lists Nagad as unavailable.
Banks, cardsNot started The checkout method picker already lists them as unsupported, so adding one does not change the buyer's flow.

Adding one

  1. Send a small transfer and save the exact confirmation text.
  2. Add it to apps/web/lib/parsers/fixtures/ with the fields you expect.
  3. Write the regexes in apps/web/lib/parsers/<provider>.ts until it passes.
  4. Optionally add a walkthrough in apps/web/components/pay/guides.tsx. A provider with no guide degrades to plain instructions rather than showing somebody else's screens.

Fixtures come first, on purpose. A parser written against a guess is a parser that silently mis-reads money. Every provider starts from a real captured message or it does not ship.
