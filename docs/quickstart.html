Quick start

Add Jomma to your store

Three steps. Create a payment, send the buyer to a page, handle the webhook. Everything else in these docs is reference.

Before you start

You need three things from a running Jomma instance:

WhatWhere from
Your instance URLWherever you deployed it, e.g. https://pay.yourshop.com
An API key (jm_live_...)Dashboard > Apps > create a key. Shown once.
A webhook signing secretDashboard > Apps > add an endpoint.

Do not have an instance yet? Running it gets you one locally in about five minutes.

Every money value is in poisha, the minor unit. Tk 1,250.00 is 125000. This is so no floating-point value ever touches a payment. Multiply by 100 on the way in and divide on the way out.

The three steps

Create a payment at checkout

When the buyer confirms their order, ask Jomma for a reference code. Send your order id as the Idempotency-Key so a retry cannot allocate a second code. 

curl -X POST https://pay.yourshop.com/v1/intents \
  -H "Authorization: Bearer jm_live_YOUR_KEY" \
  -H "Idempotency-Key: ORD-2026-001043" \
  -H "Content-Type: application/json" \
  -d '{
    "amount": 125000,
    "client_reference": "ORD-2026-001043",
    "payer_msisdn": "8801712345678",
    "provider": "bkash",
    "ttl_seconds": 900,
    "return_url": "https://yourshop.com/orders/1043/thanks",
    "cancel_url": "https://yourshop.com/cart",
    "metadata": { "store_id": "st_912" }
  }'
{
  "id": "int_01M1PEP3ZZEEC99NQ5CM1H6W1Q",
  "status": "open",
  "amount": 125000,
  "received_amount": 0,
  "ref_code": "7CX4Z8ZS",
  "receiving_account": {
    "provider": "bkash",
    "msisdn": "8801611223344",
    "display_name": "Your Shop"
  },
  "client_reference": "ORD-2026-001043",
  "shortfall": 125000,
  "excess": 0,
  "payments": [],
  "expires_at": "2026-09-04T14:05:00Z",
  "created_at": "2026-09-04T13:50:00Z"
}

Store id against your order. You will need it in step two, and it is what the webhook refers back to.

Send the buyer to the pay page

https://pay.yourshop.com/pay/int_01M1PEP3ZZEEC99NQ5CM1H6W1Q

That page does the rest:

  • Shows the receiving number, the exact amount, and the reference code, each with a copy button.
  • Asks which number they are paying from, if your server did not say — without it, nothing auto-matches.
  • Plays an animated walkthrough of the provider's Send Money flow with those values in it, for both the app and *247#.
  • Offers a QR that opens the same page on a phone, for a buyer sitting at a laptop.
  • Turns into a receipt the moment the payment matches, and redirects to your return_url.

You write no polling code. If you would rather render your own screen, see building your own checkout.

Handle the webhook

This is the one that matters: it is how your store learns the money arrived. Verify the signature before trusting anything in the body. 

import { createHmac, timingSafeEqual } from 'node:crypto'

export async function POST(req: Request) {
  // The RAW body. Parsing and re-serialising changes the whitespace and the
  // signature will not match.
  const raw = await req.text()
  const header = req.headers.get('x-jomma-signature') ?? ''

  const t = header.match(/t=(\d+)/)?.[1]
  const v1 = header.match(/v1=([a-f0-9]+)/)?.[1]
  if (!t || !v1) return new Response('bad signature', { status: 400 })

  // A valid signature replayed tomorrow is still a replay.
  if (Math.abs(Date.now() / 1000 - Number(t)) > 300) {
    return new Response('stale', { status: 400 })
  }

  const expected = createHmac('sha256', process.env.JOMMA_WEBHOOK_SECRET)
    .update(t + '.' + raw)
    .digest('hex')

  const a = Buffer.from(expected)
  const b = Buffer.from(v1)
  if (a.length !== b.length || !timingSafeEqual(a, b)) {
    return new Response('bad signature', { status: 400 })
  }

  const event = JSON.parse(raw)

  // At-least-once delivery: the same event.id can arrive twice.
  if (await alreadyProcessed(event.id)) return new Response('ok')

  switch (event.type) {
    case 'payment.succeeded':
      await fulfilOrder(event.data.client_reference)
      break
    case 'payment.partial':
      await noteShortfall(event.data.client_reference, event.data.shortfall)
      break
    case 'payment.expired':
      await releaseStock(event.data.client_reference)
      break
    case 'payment.reversed':
      await unfulfilOrder(event.data.client_reference)
      break
  }

  await markProcessed(event.id)
  return new Response('ok') // any 2xx stops the retries
}

That is the whole integration. A store that only handles payment.succeeded and payment.expired is already working correctly — the rest refine it.

Testing the flow

You do not need to move real money to exercise the whole path. The signed ingest endpoint accepts a message as if a phone had captured it: 

# 1. Create an intent and note its ref_code and receiving msisdn.
# 2. Feed in a message carrying that code, signed with your ingest secret.

BODY='{"msisdn":"8801611223344","raw":"You have received Tk 1,250.00 from 01712345678. Ref 7CX4Z8ZS. Fee Tk 0.00. Balance Tk 5,000.00. TrxID TEST12345 at 04/09/2026 19:54","source":"generic_webhook"}'
TS=$(date +%s)
SIG=$(printf '%s.%s' "$TS" "$BODY" | openssl dgst -sha256 -hmac "$WEBHOOK_SIGNING_SECRET" -hex | sed 's/.* //')

curl -X POST https://pay.yourshop.com/ingest/v1/webhook \
  -H "Content-Type: application/json" \
  -H "X-Jomma-Signature: t=$TS,v1=$SIG" \
  -d "$BODY"

Then poll the intent, or watch your webhook endpoint. Three things must line up or it will not match:

  • The Ref in the message equals the intent's ref_code.
  • The sender number equals the intent's payer_msisdn.
  • The timestamp in the message falls inside the checkout window.

If it does not match, the matching rules explain exactly which condition failed and why.

Cases to handle

The buyer pays too little

The intent becomes partial and you get payment.partial with a shortfall. The same reference code stays valid, so they can send the rest and it accumulates. Extend the deadline if they need longer: 

curl -X POST https://pay.yourshop.com/v1/intents/int_01M1.../extend \
  -H "Authorization: Bearer jm_live_YOUR_KEY" \
  -H "Content-Type: application/json" \
  -d '{"ttl_seconds": 900}'

The buyer pays too much

The order completes — you get payment.overpaid with an excess, and the intent is settled. Jomma cannot refund; the buyer can raise a request from the pay page, which reaches you as payment.refund_requested.

The buyer forgot the reference

Nothing auto-matches, by design. The pay page offers a manual box after about forty seconds where they enter the TrxID from their confirmation, and Jomma settles it if the sender and account line up. You can do the same server-side with POST /v1/submissions.

Nobody pays

At ttl_seconds the intent expires and you get payment.expired. Release the stock. The reference code is consumed and never reissued.

Every receiving account is down

POST /v1/intents returns 503 no_healthy_account. Do not show a pay page — there is no number for the buyer to send to. Fall back to another payment method, or tell them to try shortly.
